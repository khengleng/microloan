Design proposal · Web workspace

One workspace for every role, built from what each person is allowed to do

Magic Money staff use two apps that grew side by side: the original lending screens and the configurable lending platform. Navigation is decided by four legacy role names, so most people see the wrong things. This proposal puts everyone in one workspace whose menus, home queue and buttons come from the same permission engine the API already enforces.

Principles

Six rules the whole design follows

1 · one model

The lending permission engine decides everything

Legacy roles are mapped to access roles once, then retired from the UI. Menus, queues and buttons all read the same grants the API checks.

2 · work first

Home is your queue, not a dashboard

Each person opens to the things waiting for them: to approve, to prepare, to chase. Charts move to Reports.

3 · find by name

Search a customer, not a module

One search finds a borrower, loan, facility, application or case by name, phone, reference or ID, whichever stack it lives in.

4 · explain refusals

A blocked button says why and what would unblock it

"Someone else must approve what you prepared" beats a 403. The reason comes from the policy decision itself.

5 · hide vs. show

Hide what your role can never do. Show what you could do in a different situation.

No permission: the item is absent. Permission but blocked by state, scope, MFA or limit: the item shows, disabled, with the reason.

6 · Khmer first-class

Every screen ships in English and Khmer

Including lending, accounting and the portal. Money shows as $1,250.00 and ៛5,125,000 with the currency's own minor units.

Information architecture

Nine areas, each shown only to people who hold a permission inside it

The legacy and lending screens merge into one tree. An area appears when the user holds any permission listed for one of its pages; a page appears when the user holds one of its permissions.

Interaction pattern

One button, seven possible answers

The policy engine already checks seven layers in order and reports every failure. The UI turns each layer into a sentence the person can act on. Example: Approve disbursement on LN-2026-00412, $8,400.00, Toul Kork branch.

Record page

The loan page groups actions by what you are trying to do

Today the loan page stacks panels: disbursement, repayment, settlement, reversal, write-off, and a placeholder that says refinancing is unavailable. The proposal keeps the facts and history on the left, and puts actions in a right rail grouped by intent. Each group shows only the actions the loan's state allows.

Phone first, Khmer by default

Borrowers sign in with a phone number and a one-time code. The first screen answers one question: how much and by when. Paying, asking for relief and reading documents are the only other actions.

Every number that changes the borrower's cost is stated in plain terms before they accept: the new instalment, the new end date, and how much more interest they pay. The current portal already has the restructure request and acceptance flows; this design changes their order and wording, not their rules.

Needs: SMS delivery for one-time codes (today codes are dropped when no SMS provider is set), and rate limits on code requests.

Platform console

The platform operator works across organisations, never inside one

The platform operator (SUPERADMIN) gets a separate console: organisations, plan payments to confirm, subscription plans, platform flags and the platform audit log. The policy engine already blocks platform users from tenant data, so the console never links into a tenant's loans. The top bar shows "Platform" in place of a branch, so nobody mistakes which world they are in.

Delivery

Four releases, each usable on its own

Shell and access

  • /me/access, /me/work, fail-closed capabilities
  • New sidebar and top bar (search, business date, scope chip, MFA state)
  • Role migration and Team & roles page
  • Home queue per person

One loan, one place

  • Unified search and loan page with the action rail
  • Screens for the API-only features: facilities, rate resets and benchmark rates, groups, negotiated settlement, recoveries, holiday programmes, refinance
  • Legacy loan pages redirect into the unified page

Khmer and the portal

  • Translation keys for every lending, accounting and admin screen
  • Portal redesign, phone first

Retire the duplicates

  • Remove legacy collections, restructure, write-off and audit screens once their data is reachable from the unified pages
